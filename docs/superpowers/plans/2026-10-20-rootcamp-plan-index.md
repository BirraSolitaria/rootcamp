## Режим разработки на Windows

- Docker Desktop + WSL2; Testcontainers, compose-стенды и драйвер `runc-dev` работают там.
- `runc-dev`: только `NODE_ENV !== 'production'`, все образы практик подменяются на `rc/test-shell`, без systemd, userns, зеркал и iptables. systemd- и dind-инциденты, изоляция и время готовности проверяются **только на VPS** (M4b).
- `.gitattributes` с `eol=lf` обязателен: скрипты практик исполняются в Linux.
- shellcheck: бинарь из PATH или фолбэк `koalaman/shellcheck` в Docker.

## Решения сверх спецификации (сводка)

1. Drizzle-схема в `packages/db` (её используют `api` и `sandboxd`); миграции по-прежнему в `apps/api/drizzle/`.
2. `content-dist` — две ветки: `public/<hash>` (Caddy) и `server/<hash>` (только `api`). Хеш версии включает скрипты практик.
3. R15/R16 применяются только к трекам `status: complete`; R15 не требует `order_steps`.
4. Практика доступна, если пройден ближайший предшествующий узел `kind: lesson` (узлы-практики друг друга не блокируют).
5. Неподтверждённому email разрешены также `PATCH /api/me`, `/api/health`, `GET /api/content/version`.
6. Регистрация сразу создаёт сессию (экран «Проверь почту» требует входа).
7. Тело `POST /api/sessions/:id/answer` получает `presentation` для идемпотентности.
8. Внутренний API `sandboxd`: поля `title`, `test`; `GET /api/runs/:id` отдаёт `usage`; drain — `settings.sandboxes_drained`; `queue_timeout` — `stopped` с причиной.
9. Коды WS: молчание клиента — 4100 (а не 4008), третье соединение — 4409.
10. Неделя лидерборда считается по `created_at` в MSK.
11. Письма: первая отправка сразу + 5 повторов (1, 5, 15, 60, 240 мин).
12. `alert_events` — единая очередь алертов для `api` и shell-скриптов.
13. Тестовые вспомогательные средства: overlay-узлы контента для e2e, `dev:seed-progress` (запрещён в production).

## Найденные дыры и противоречия в спецификации

- §5.1 закрывает для неподтверждённых всё, кроме `/api/auth/*` и `GET /api/me`, а §9 требует от них `PATCH /api/me {email}`.
- §5.2: код 4008 («60 с без кадров») совпадает с `4000 + индекс(banned)`.
- §4.3: R15/R16 из DockerLingo (доля каждого типа ≥ 10 %, 40–60 уроков) несовместимы с T1 `partial` (5 уроков); правило R15 с шестым типом ломает T7.
- §3.5: хеш «от JSON курса» не меняется при правке `check.sh`, а путь кешируется как immutable.
- §3.4/§3.2: схема БД в `apps/api`, хотя `sandboxd` пишет `sandboxes`.
- §9 обещает идемпотентность по `presentation`, но в теле `answer` (§5.1) этого поля нет.
- §10.5/§11.5: `practice:test` «вне очереди» и `sandboxes:drain` не имеют механизма во внутреннем API §5.3.
- §8.1 «строка CPU/RAM» на экране практики — данных нет в `GET /api/runs/:id`.
- §5.1 «урок непосредственно перед узлом» неоднозначно для двух практик подряд (T1.1).
- §4.4: у `sandboxes.state` нет `queue_timeout`, хотя у `practice_runs` он есть; нет механизма уведомления `api` о смене состояния песочницы (решено опросом и заданием `runs-sync`).
- §10.4 сценарий 5: фикстура `inc-e2e-touch` не имеет узла в пути, без него практика `locked`.
- §9 «5 попыток» при перечислении пяти задержек — неясно, считается ли первая отправка.
- Мелочь: DockerLingo на React 19 / TS 6, спецификация фиксирует React 18 / TS 5 — переносимые компоненты переписываются, так что это не мешает, но версии стоит подтвердить.
